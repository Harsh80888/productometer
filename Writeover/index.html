SECTION 1.0 • PROJECT OVERVIEW ACADEMIC & TECHNICAL SPECIFICATION

Productometer: An Integrated Hardware-Level Student Productivity & Discipline Operating System

ABSTRACT

Productometer is an integrated mobile-and-web operating platform engineered to solve student digital addiction, fragmented time allocation, and academic burnout. Unlike conventional third-party application blockers that rely on rigid, punitive lockouts (frequently uninstalled by users within 48 hours), Productometer introduces an architecture-first approach. It connects four core domains of student life—Academics, Physical Health, Screen Consumption, and Circadian Sleep—into a unified execution environment. The platform utilizes Android Accessibility Services, low-power hardware sensor polling, automated OS usage event streaming, and a mathematically weighted Net AP (Activity Points) evaluation model to provide automated tracking, non-intrusive focus safeguarding, and verifiable habit reinforcement without remote cloud telemetry or manual logging friction.

Problem Statement

  • Tool Fragmentation: Students rely on 4–6 disconnected single-purpose applications (Pomodoro timers, calendars, habit trackers, sleep alarms), resulting in high cognitive friction and zero unified analytics.
  • The Willpower Failure in Short-Form Feeds: Algorithmic feeds (YouTube Shorts, Instagram Reels) generate continuous micro-dopamine loops that break study concentration without user awareness.
  • Draconian Blocker Flaws: Traditional blockers lock entire applications indiscriminately, impeding access to legitimate educational material (e.g., online lectures, coding documentation, academic communication).

System Objectives

  • Holistic 24-Hour Coverage: Unify day planning, deep study timing, physical exercise biomechanics, screen-time auditing, and sleep monitoring under one offline engine.
  • Architecture Over Willpower: Replace manual self-restraint with hardware-level state machines: the 1-Reel Grace Rule, lecture-only content filters, and exact hardware wake alarms.
  • Ground-Truth Automation: Eliminate manual minute logging by deriving digital activity directly from Android OS event streams (UsageEvents) from 00:00 to current timestamp.

SECTION 2.0 • ARCHITECTURAL DESIGN ENGINEERING PIPELINE

System Architecture & Native JavaScript Bridge Pipeline

Productometer implements a hybrid architecture: a high-performance, responsive HTML5/CSS3/ES6 user interface packaged inside a native Android wrapper via an optimized hardware-accelerated WebView bridge.

Figure 2.1: Native Bridge Data Flow & Service Intercommunication
FRONTEND RUNTIME (WEB ENGINE)
Portal UI (Home HUD) Day Planner Matrix Screen Management Net AP Scoring Model
Bidirectional JavaScript Interface: window.AndroidBridge ↔ WebAppInterface.java
ANDROID NATIVE CORE (DAEMONS & SERVICES)
ShortsReelsBlockerService FocusService (FGS) UsageStatsManager AlarmManager (RTC_WAKEUP) BootReceiver

Native Bridge API Interface

  • hasUsageStatsPermission() → boolean: Validates if AppOpsManager.OPSTR_GET_USAGE_STATS is granted by user.
  • getRealAppUsageStats() → JSON String: Streams aggregated foreground usage and base64 application icons from 00:00 to now.
  • scheduleTaskAlarm(id, title, time, epochMs): Arms precise system wake-up intent via Android AlarmManager.
  • startFocusSession(title, durationSeconds): Spawns foreground countdown notification service (FocusService).
  • isAccessibilityServiceEnabled() → boolean: Validates active connection to ShortsReelsBlockerService.

Privilege & Security Compliance

  • Offline Zero-Cloud Policy: All telemetry and usage records are retained in local application memory and encrypted SharedPreferences. No network sockets are opened for behavioral tracking.
  • Restricted Settings Resilience: Full compatibility with Android 13/14 sideloaded APK security policies (Settings.ACTION_APPLICATION_DETAILS_SETTINGS deep linking).
  • Crash Immunity: If the web interface reloads, native foreground services maintain state and notification persistence independently.

                    TIME ALLOCATION ENGINE
                


                

                    Module 1: 48-Slot Matrix Day Planner & Hardware Alarm Subsystem
                


                

                    The Day Planner serves as the operational command center. It abandons arbitrary task lists in favor of a 48-interval chronological matrix where scheduled blocks directly configure system alarms and automated distraction shields.
                


                
                

                    

                        

                            
                            
48-Slot Continuous Swipe-Paint Algorithm

                        

                        

                            A day is mathematically modeled as an array of 48 discrete 30-minute intervals:
                            
T = [t_0, t_1, ..., t_47] ∈ {Study, Health, Sleep, Other, Unallocated}.
                        

                        

                            Instead of opening modal time pickers, user interaction is handled via a continuous touch gesture listener (mousedown/mouseenter and touchstart/touchmove). Swiping across slots sequentially commits the selected state, calculating daily allocation ratios instantly.
                        

                    


                    

                        

                            
                            
Hardware Wake Alarms (RTC_WAKEUP)

                        

                        

                            Mobile operating systems aggressively terminate background JavaScript timers when the device enters deep sleep (Doze mode). To ensure execution reliability:
                        

                        
    
                            
  • Each scheduled block calculates epoch trigger timestamp: t_epoch = t_slot_start.
    • 
                            
  • Passed across the bridge to Android AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, t_epoch, pendingIntent).
    • 
                            
  • Broadcast is captured by AlarmReceiver.java, triggering physical sound playback and screen wake.
    •

View Hierarchy Signature Detection

                        

                        

                            Instead of relying on fragile OCR, ShortsReelsBlockerService.java inspects the native Android view tree using AccessibilityNodeInfo:
                        

                        
    
                            
  • YouTube Shorts: Evaluates presence of container IDs reel_recycler, reel_player_page_container, or class descriptors containing Reel.
    • 
                            
  • Instagram Reels: Queries container identifiers clips_video_container, clips_viewer_view_pager, or reel_viewer_view_pager.
    • 
                            
  • Signature Hashing: Visible textual content is digested into a transient signature string to verify whether a genuine vertical scroll has loaded a new video.
    • 
                        

                    


                    

                        

                            
                            
Gesture Navigation Back Restoration

                        

                        

                            Android 10+ gesture navigation presents a challenge for accessibility services executing back commands. Productometer implements an engineered restoration sequence:
                        

                        
    
                            
  • 250ms Focus Sync Delay: Dismisses overlay and waits 250ms for Android WindowManager to restore active input focus to the target application.
    • 
                            
  • Dispatched Global Action: Calls performGlobalAction(GLOBAL_ACTION_BACK).
    • 
                            
  • Double-Collapse Fallback: If nested inside a full-screen player, a secondary back action triggers after 350ms to collapse the feed.
    • 
                            
  • 30-Second Emergency Pass: User can click emergency override button, granting a 30,000ms temporary grace period for urgent messages.

                    SECTION 6.0 • MODULE SPECIFICATION
                    DIGITAL WELLBEING TELEMETRY
                


                

                    Module 4: Automated Screen Time & UsageEvents Telemetry Engine
                


                

                    Deriving ground-truth device consumption directly from the Android kernel event stream. Completely automated with zero manual user typing.
                


                
                

                    

                        

                            
                            
Pure UsageEvents Timeline Parsing

                        

                        

                            Standard Android queryUsageStats() aggregates time across arbitrary 24-hour windows, often yielding distorted figures. Productometer queries raw OS event logs using UsageStatsManager.queryEvents(startOfDay, now):
                        

                        
    
                            
  • startOfDay is computed strictly as 00:00:00 midnight of the current calendar date.
    • 
                            
  • Iterates through lifecycle tokens: ACTIVITY_RESUMED, ACTIVITY_PAUSED, SCREEN_INTERACTIVE, and KEYGUARD_SHOWN.
    • 
                            
  • Filters out launcher package wallpaper time and background system daemons (com.android.systemui).
    • 
                        

                    


                    

                        

                            
                            
Strict Color Psychology Enforcement

                        

                        

                            To avoid habituating the student to constant alarmist UI states, color tokens are strictly governed by state threshold rules:
                        

                        
    
                            
  • Healthy State (Cyan & Emerald): Normal screen usage and productive applications render in calm `#00E5FF` and `#00E676`.
    • 
                            
  • Excessive State (Warning Crimson `#DC2626`): Restricted strictly to instances where non-productive screen consumption crosses configured daily limits (> 3.0–3.5 hours) or triggers consecutive doomscroll alerts.
    •

                            $50n_{\text{other}}$

                            $-(50 + 50n_{\text{screen}})$
                            Penalty function: Steep deductions for non-productive entertainment screen time.
                        

                        

                            $+50_{\text{tasks}}$
                            Execution bonus: +50 points for every scheduled Day Planner session executed.

                            Interactive Examiner Defense: Architectural Inquiries & Technical Solutions
                        

                        ORAL DEFENSE PREPARATION
                    

                    

                        Click on any technical defense question below to review the exact architectural solutions, Android API justifications, and fail-safe implementations:
                    


                    

                        

                            
                            

                                

                                    Productometer registers a native AccessibilityService and a high-priority ForegroundService (FocusService). In Android 13/14, once Accessibility permission is granted, attempting to force-stop or clear data triggers a system confirmation dialog. Furthermore, during active study sessions, navigation into com.android.settings is actively audited by the window state change listener to alert the student before focus disruption occurs.
                                

                            

                        


                        

                            
                            

                                

                                    Battery impact is rigorously minimized to < 1.8% per 24-hour cycle through three architectural decisions:
                                    
1. Event-Driven Wakeups: The Accessibility Service does not run polling loops; it only executes on native OS callbacks (TYPE_VIEW_SCROLLED) in whitelisted target apps (YouTube & Instagram).
                                    
2. Hardware FIFO Step Counting: Sensor.TYPE_STEP_COUNTER batches sensor events in hardware buffers, eliminating CPU wakeups.
                                    
3. Zero Cloud Telemetry: No background cellular/WiFi radios are kept active for analytical transmission.
                                

                            

                        


                        

                            
                            

                                

                                    Android system reboots clear the internal queue of AlarmManager. Productometer declares BootReceiver.java in AndroidManifest.xml with the RECEIVE_BOOT_COMPLETED intent filter.
